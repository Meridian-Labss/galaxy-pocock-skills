  A good PR description opens with a short, plain-language title naming the work
  (not a code identifier or ticket number), then summarises what changed and why
  before any implementation detail. It names the specific evidence that the fix
  works (the failing-then-passing test, the full suite passing) rather than a
  vague "tested it" claim. It does not force the reader to open another file or
  look up an identifier to understand the summary. It is short enough to read in
  a few seconds and still convey the outcome.
